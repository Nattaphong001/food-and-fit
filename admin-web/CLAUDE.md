# Food & Fit — workspace map

3 project แยกกัน คนละ dir อย่าสับสน:

| ส่วน | path | รันแบบ | port |
|---|---|---|---|
| API (Go) | `C:\xampp\htdocs\food_and_fit_api` | `go run main.go` | 8081 |
| frontend user (member) | `C:\myFutter68\myapp` | `flutter run` → มือถือ/emulator | - |
| front admin (นี่) | `C:\myFutter68\myapp_admin` | `flutter run -d chrome --web-port=8090` | 8090 |

- ก่อนรัน API: เปิด XAMPP MySQL ก่อนเสมอ
- admin web ต้องรัน port 8090 ตรงกับ `ALLOWED_ORIGINS` ใน `food_and_fit_api\.env` — เปลี่ยน port ต้อง sync ทั้งสองที่
- ถ้า bind port fail (errno 10048) แปลว่ามี process ค้าง → `netstat -ano | findstr ":8090"` หา PID แล้ว `taskkill /PID <pid> /F`
- ทำงานอยู่ path ไหน เช็คก่อนรัน command ทุกครั้ง (workspace มีหลาย working directory พร้อมกัน)

# กฎเหล็ก — ห้ามข้ามแม้ไม่มีใครสั่งซ้ำ

โปรเจกต์นี้คืองาน "เพิ่ม admin web" แยกออกจากของเดิมที่ใช้งานได้อยู่แล้ว
(มือถือ + API) กฎพวกนี้ป้องกันไม่ให้งานใหม่ไปทำของเดิมพัง:

1. **ห้ามแก้ไฟล์ใน `C:\myFutter68\myapp`** (แอปมือถือ) เด็ดขาด
   ถ้าต้องใช้โค้ด/หน้าจอจากที่นั่น ให้ **copy** มาไว้ที่ `myapp_admin` เท่านั้น
   ห้ามแก้ไฟล์ต้นทาง
2. **ห้ามแก้ endpoint เดิมใน Go** ที่แอปมือถือเรียกใช้อยู่ — ต้องการอะไรเพิ่มให้
   **เพิ่ม endpoint ใหม่** เสมอ (เช่น เติม `/admin/...`) ไม่ใช่ไปแก้ signature/response
   ของ endpoint เดิม
3. **ห้ามแก้สูตรคำนวณ** (BMR / TDEE / Target / METs / 1RM / Macronutrients)
   สูตรทั้งหมดอยู่ใน `services/calculator.go` (`CalculateGoals`) ห้ามเขียนสูตรซ้ำ
   ที่อื่น ถ้า endpoint ใหม่ต้องคำนวณค่าพลังงาน ให้เรียกฟังก์ชันนี้เสมอ
4. **ตารางแม่ (`nutrition`, `cardio`, `nutrition_category`, `cardio_category`)
   ไม่มีคอลัมน์ `created_at`/`updated_at`** — เรียง "ล่าสุด" ให้ใช้ `PK DESC`
   ห้ามเพิ่มคอลัมน์เองโดยไม่ถาม เพราะต้องแก้ ER Diagram + เอกสารบทที่ 4 ตามไปด้วย
5. **ลบข้อมูลที่มี FK ผูกอยู่ (เช่นลบอาหารที่มีคนกินไปแล้ว) ให้ soft delete**
   (เพิ่มคอลัมน์ status/hidden ซ่อนจากแอปมือถือ แต่เก็บ history ไว้) — ตัดสินใจแล้ว
   (2026-08-22) ว่ายอมแก้ schema + ER Diagram + บทที่ 4 เพื่อความปลอดภัยของข้อมูล
   แทนที่จะบล็อกการลบเฉยๆ ดูรายละเอียดใน memory `admin-ux-decisions` (D-2)
6. **ทำทีละไฟล์/ทีละ endpoint เวลา refactor หรือย้ายโค้ดชุดใหญ่** อย่ารวบทำ
   หลายไฟล์ในคำสั่งเดียว จะ debug ยากเวลามีอะไรพัง
7. เจอจุดที่โค้ดจริงไม่ตรงกับพจนานุกรมข้อมูล (Data Dictionary) ในบทที่ 4 ของเล่ม
   ให้ **หยุดแล้วรายงาน** ห้ามเดาว่าอันไหนถูกแล้วแก้เอง

**เอกสารอ้างอิงเพิ่มเติม** (อ่านก่อนเริ่มงานที่เกี่ยวข้อง ถ้ามีไฟล์เหล่านี้ในโปรเจกต์):
- `claude_code_brief-ย้าย-admin-ไป-web.md` — ขั้นตอนย้ายหน้า admin จากมือถือมาเว็บ
- `claude_code_prompt-admin-web-ux-ui-และมาตรฐานข้อมูล.md` — สเปกฟอร์ม/ฟิลด์ต้องตรง
  พจนานุกรมข้อมูลบทที่ 4 แบบ 1:1 + มาตรฐาน layout จอกว้าง
- `claude_code_prompt-แก้-performance-admin-web.md` — แก้ปัญหา cache/navigation/fetch

# โหมดทำงาน

## Caveman Mode (โหมดพูดกระชับ ประหยัดโทเคน)
- caveman mode: **เปิดเสมอทุก session** ไม่ต้องรอสั่งใหม่

**เปิดใช้เมื่อพิมพ์:** `"enable caveman mode"` หรือ `"talk like a caveman"`
**ปิดใช้เมื่อพิมพ์:** `"disable caveman mode"` หรือ `"stop talking like a caveman"`

เมื่อเปิดโหมดนี้:

- ตอบสั้นที่สุดเท่าที่ยังสื่อสารครบ — ตัดคำฟุ่มเฟือย ไม่ทวนคำถามซ้ำ
  ไม่ต้องพูดคำนำ/คำปิดท้ายทางการ
- โค้ด/คำสั่งที่ต้องรันยังต้องแสดงครบ ห้ามตัดทอนจนใช้งานไม่ได้ —
  โหมดนี้ตัด "คำอธิบายรอบข้าง" ไม่ใช่ตัด "เนื้อหาที่จำเป็น"
- ถ้าเจอจุดที่เสี่ยง (จะแก้ endpoint เดิม, จะแตะไฟล์ในมือถือ, จะเดาแทนถาม)
  ยังต้องแจ้ง/หยุดเหมือนเดิม — caveman mode ไม่ยกเว้นกฎเหล็กด้านบน
- ค่าเริ่มต้นของทุก session ใหม่คือ **ปิด** (โหมดปกติ) จนกว่าจะพิมพ์เปิดเอง

## กฎการตอบคำถามเทียบกับคำสั่งให้ลงมือทำ

- ถ้าเป็น**คำถาม** (ไม่ใช่สั่งให้ทำ) → ตอบคำถามก่อน อย่ารีบลงมือทำโดยไม่ตอบ
- ถ้าเป็น**คำสั่งให้ทำ** ที่ scope กว้างหรือกระทบกฎเหล็กข้อไหนข้างบน →
  หยุดถามยืนยันก่อน อย่าลงมือเดาแล้วทำเลย
