# Brief สำหรับ Claude Code — ย้ายหน้า Admin จาก Flutter Mobile ไป Flutter Web

โปรเจกต์: การพัฒนาแอปพลิเคชันเพื่อการจัดการการออกกำลังกายและโภชนาการ
สแต็ก: Flutter/Dart (frontend) · Go (backend) · MySQL

**วิธีใช้ไฟล์นี้:** วางไฟล์นี้ไว้ใน root ของโปรเจกต์เว็บใหม่ แล้วบอก Claude Code ว่า
"อ่าน claude_code_brief-ย้าย-admin-ไป-web.md แล้วทำเฟส 0" — จากนั้นทำทีละเฟส
ห้ามสั่งรวบทุกเฟสในคำสั่งเดียว

---

## กฎเหล็ก (Guardrails) — ต้องปฏิบัติทุกเฟส

1. **COPY เท่านั้น ห้าม CUT** — ห้ามลบหรือแก้ไฟล์ในโปรเจกต์มือถือเดิมเด็ดขาด
   แม้จะ "ย้ายมาแล้ว" ก็ให้ของเดิมคงอยู่ ไม่งั้นถ้าเว็บไม่เสร็จทันจะไม่มีของโชว์
2. **ห้ามแก้ endpoint เดิมใน Go** ที่แอปมือถือเรียกใช้อยู่
   ถ้างาน Admin ต้องการข้อมูลรูปแบบอื่น ให้ **เพิ่ม endpoint ใหม่** เท่านั้น
   (เช่น `GET /admin/members?page=1&search=`) ไม่ใช่ไปแก้ของเดิมให้รองรับทั้งสองแบบ
3. **ห้ามแก้สูตรคำนวณ** (BMR / TDEE / Target / METs / 1RM / Macronutrients)
   สูตรทั้งหมดอ้างอิงบทที่ 2 ของเล่มโปรเจกต์ ถ้าเจอจุดที่คิดว่าผิด ให้ "รายงาน" ไม่ใช่ "แก้เอง"
4. **ห้ามแก้ business logic ฝั่ง Go** — งานนี้คืองานย้าย UI ไม่ใช่งาน refactor
   โดยเฉพาะ `services/calculator.go` (`CalculateGoals`) และ logic effective-record
   ใน `analytics_controller.go` ห้ามแตะ
5. **ทำทีละเฟส หยุดรอยืนยันทุกครั้ง** — จบเฟสแล้วให้สรุปว่าทำอะไรไปบ้าง
   (ระบุ file:line) แล้วหยุด ห้ามข้ามไปเฟสถัดไปเอง
6. **ห้ามสร้างข้อมูลปลอม/mock ทับของจริง** ถ้า API ยังไม่พร้อม ให้บอกตรง ๆ ว่ายังไม่พร้อม
7. **คงระบบคอมเมนต์ tag เดิม** (`[PAGE]` / `[FEATURE]` / `[FUNCTION]` ฯลฯ)
   เมื่อ copy ไฟล์มา ให้เก็บคอมเมนต์เดิมไว้ และอัปเดต `[PAGE_ROUTE]` ให้ตรงกับ route ใหม่บนเว็บ

## เฟส 0 — สำรวจของเดิม (ยังไม่เขียนโค้ด)

**เป้าหมาย:** รู้ scope งานทั้งหมดก่อนลงมือ

### Prompt สำหรับ Claude Code

```
อ่าน guardrails ในไฟล์ brief ก่อน แล้วทำเฟส 0 เท่านั้น: สำรวจอย่างเดียว ห้ามแก้ไฟล์ใด ๆ

ในโปรเจกต์ Flutter มือถือเดิม (path: <ใส่ path>) ให้หา:
1. หน้าจอทั้งหมดที่เป็นของ Admin — ค้นจาก grep "\[PAGE\]" ใน lib/ และดูว่าหน้าไหน
   ใช้เฉพาะ Admin (ดูจาก route guard / role check / ชื่อไฟล์)
2. แต่ละหน้า Admin เรียก API endpoint ไหนบ้าง (ระบุ method + path)
3. package/plugin ที่หน้าเหล่านั้นใช้ แล้วเช็คว่าตัวไหน "ไม่รองรับ Flutter Web"
   (เช่น flutter_secure_storage, path_provider, camera, dart:io)
4. วิธีเก็บ token/session ปัจจุบัน ใช้อะไร เก็บที่ไหน

ในโปรเจกต์ Go backend (path: <ใส่ path>) ให้หา:
5. endpoint ทั้งหมดที่เป็นของ Admin (ดูใน routes/ และ controllers/)
6. middleware ตรวจสอบสิทธิ์ Admin ทำงานยังไง (ไฟล์ไหน บรรทัดไหน)
7. มี CORS middleware อยู่แล้วหรือยัง

ผลลัพธ์: ตอบเป็นตาราง 3 ตาราง (หน้าจอ Admin / endpoint ที่ใช้ / package ที่มีปัญหากับเว็บ)
อ้างอิง file:line จริงทุกแถว ห้ามเดา แล้วหยุดรอคำสั่งต่อไป
```

### เช็คก่อนไปเฟส 1
- [ ] ได้ลิสต์หน้า Admin ครบ พร้อม path ไฟล์จริง
- [ ] รู้ว่ามี package ตัวไหนบ้างที่ต้องหาตัวแทนบนเว็บ
- [ ] รู้ว่า token เก็บด้วยอะไร

## เฟส 1 — ทำให้เว็บ "ยิง API ติด" ก่อนทุกอย่าง

**เป้าหมาย:** ยังไม่ต้องสวย แค่ให้เว็บคุยกับ backend ได้จริง
**ถ้าเฟสนี้ไม่ผ่าน ห้ามไปต่อ** เพราะทุกหน้าหลังจากนี้จะพังด้วยสาเหตุเดียวกัน

### Prompt สำหรับ Claude Code

```
ทำเฟส 1 เท่านั้น

1. เพิ่ม CORS middleware ใน Go backend
   - ระบุ allowed origin เป็นค่าที่อ่านจาก environment variable ไม่ hardcode
   - dev ใช้ http://localhost:<port ของ flutter web>
   - ห้ามใช้ Allow-Origin: * (เหตุผลด้านความปลอดภัย เพราะมีการส่ง token)
   - ต้องรองรับ preflight OPTIONS และ header Authorization
   - เพิ่มเป็น middleware ใหม่ ห้ามแก้ handler เดิมของ endpoint ใด ๆ

2. ในโปรเจกต์เว็บใหม่ ตั้งค่า API base URL
   - ระวัง: ถ้าโปรเจกต์มือถือใช้ 10.0.2.2 (Android emulator) บนเว็บใช้ไม่ได้
     ต้องเป็น localhost หรือ IP จริง
   - ทำเป็น config แยกไฟล์ อ่านค่าได้จาก --dart-define

3. สร้างหน้าทดสอบชั่วคราว 1 หน้า มีปุ่มเดียว ยิง API ตัวใดก็ได้ที่ไม่ต้อง auth
   แล้วแสดง response ดิบบนจอ

รันด้วย flutter run -d chrome แล้วรายงานว่าได้ response กลับมาไหม
ถ้า error ให้แสดง error เต็ม ๆ พร้อมวิเคราะห์สาเหตุ แล้วหยุด
```

### เช็คก่อนไปเฟส 2
- [ ] เปิดเว็บบน Chrome แล้วกดปุ่มทดสอบ ได้ข้อมูลจริงกลับมา
- [ ] ไม่มี CORS error ใน console ของ browser

## เฟส 2 — Vertical slice แรก: Login + Role Guard + โครง Layout

**เป้าหมาย:** login เข้าเว็บได้ และ user ธรรมดาเข้าไม่ได้

### Prompt สำหรับ Claude Code

```
ทำเฟส 2 เท่านั้น

1. copy หน้า login + auth service จากโปรเจกต์มือถือมาที่โปรเจกต์เว็บ
   (COPY เท่านั้น ห้ามแตะไฟล์ต้นทาง)

2. แก้เฉพาะส่วนที่ใช้บนเว็บไม่ได้:
   - ถ้าเดิมใช้ flutter_secure_storage ให้เปลี่ยนเป็นวิธีที่รองรับเว็บ
     และอธิบายข้อแลกเปลี่ยนด้านความปลอดภัยให้ฟังก่อนเลือก ห้ามเลือกเอง
   - ถ้ามี import dart:io ให้หาทางเลี่ยง

3. เพิ่ม role guard:
   - login สำเร็จ → เช็ค role จาก response
   - ถ้าไม่ใช่ Admin → ปฏิเสธ + ล้าง token ทันที + แสดงข้อความชัดเจน
   - ใช้ระบบสิทธิ์เดิมของ backend ห้ามสร้างระบบ auth ใหม่

4. สร้างโครง layout กลางสำหรับทุกหน้า Admin (ใช้ซ้ำได้):
   - sidebar เมนูซ้าย + พื้นที่เนื้อหาขวา (เหมาะกับจอกว้าง ไม่ใช่ layout มือถือ)
   - ยังไม่ต้องใส่เมนูจริงครบ ใส่ placeholder ไว้ก่อน

5. ลบหน้าทดสอบชั่วคราวจากเฟส 1 ออก

ทดสอบ 2 เคส: login ด้วย Admin ต้องเข้าได้ / login ด้วย user ธรรมดาต้องถูกปฏิเสธ
รายงานผลแล้วหยุด
```

### เช็คก่อนไปเฟส 3
- [ ] login ด้วยบัญชี Admin เข้าได้ เห็นโครง layout
- [ ] login ด้วยบัญชี user ธรรมดา ถูกปฏิเสธจริง
- [ ] refresh หน้าเว็บแล้ว session ยังอยู่ (ไม่หลุด login)

## เฟส 3 — ย้ายหน้า Admin ทีละหน้า (วนซ้ำ)

**เป้าหมาย:** ทำทีละหน้า ให้เสร็จจริงก่อนขึ้นหน้าถัดไป
**ลำดับ:** เริ่มจากหน้าที่ **อ่านอย่างเดียว** ก่อน แล้วค่อยไปหน้าที่มีเพิ่ม/แก้/ลบ

### Prompt สำหรับ Claude Code (ใช้ซ้ำทีละหน้า)

```
ทำเฟส 3 สำหรับหน้า "<ชื่อหน้า>" เท่านั้น หน้าเดียว ห้ามทำหน้าอื่นพร้อมกัน

1. copy ไฟล์หน้าจอนี้จากโปรเจกต์มือถือมา (COPY เท่านั้น)
2. เก็บคอมเมนต์ tag เดิมทั้งหมด ([PAGE] / [FEATURE] / [FUNCTION] ...)
   แต่อัปเดต [PAGE_ROUTE] ให้ตรงกับ route บนเว็บ
3. แก้ให้ compile ผ่านบนเว็บ — ถ้าติด package ที่ไม่รองรับ ให้เสนอทางเลือกก่อน
   ห้ามตัดฟีเจอร์ทิ้งเงียบ ๆ
4. ปรับ layout ใหม่ให้เหมาะกับจอกว้าง:
   - ListView แบบมือถือ → DataTable หรือตารางที่มีหัวคอลัมน์
   - เพิ่มช่องค้นหา + แบ่งหน้า ถ้าข้อมูลเยอะ
   - ห้าม resize ของมือถือมาแปะเฉย ๆ
5. ถ้าหน้านี้ต้องการ endpoint ที่ยังไม่มี (เช่น แบ่งหน้า/ค้นหา) ให้ "แจ้ง" ก่อน
   อย่าเพิ่งเขียน ผมจะไปทำในเฟส 4 รวดเดียว

รันทดสอบกับข้อมูลจริง รายงานผลแล้วหยุด
```

### เช็คทุกหน้าก่อนขึ้นหน้าถัดไป
- [ ] เปิดหน้านี้บนเว็บได้ ไม่มี error ใน console
- [ ] เห็นข้อมูลจริงจาก DB ไม่ใช่ mock
- [ ] ถ้าหน้านี้มีการแก้ไขข้อมูล → แก้แล้วเข้า DB จริง และเปิดแอปมือถือดูแล้วข้อมูลตรงกัน
- [ ] แอปมือถือเดิมยัง build ผ่านและใช้งานได้ปกติ

## สัญญาณอันตราย — ถ้าเจอให้หยุด Claude Code ทันที

| สัญญาณ | ทำไมอันตราย |
|---|---|
| แก้ไฟล์ในโปรเจกต์มือถือเดิม | ผิดกฎข้อ 1 เสี่ยงพังของที่ใช้งานได้อยู่ |
| แก้ signature/response ของ endpoint เดิม | แอปมือถือจะพังเงียบ ๆ กว่าจะรู้ตัวคือตอนสอบ |
| เขียนสูตร BMR/TDEE/Target ซ้ำในไฟล์ใหม่ | ค่าจะ drift จากที่ระบุในบทที่ 2 |
| ทำหลายหน้าพร้อมกันในคำสั่งเดียว | แยกไม่ออกว่าอะไรพังเพราะอะไร |
| ใส่ mock data เพราะ API ยังไม่พร้อม | เข้าใจผิดว่าเสร็จแล้ว ทั้งที่ยังต่อไม่ติด |
| ลบ/ย่อคอมเมนต์ tag เดิมทิ้ง | ระบบค้นหาโค้ดของโปรเจกต์จะใช้ไม่ได้ |

## เคล็ดลับการใช้ Claude Code กับงานนี้

- **ให้มัน commit ทุกจบเฟส** จะได้ย้อนกลับได้ถ้าเฟสถัดไปพัง
- **เปิด 2 หน้าต่างแยก** — หน้าต่างหนึ่งอยู่ในโปรเจกต์เว็บ อีกหน้าต่างอยู่ในโปรเจกต์
  มือถือแบบอ่านอย่างเดียว จะลดโอกาสมันเผลอแก้ผิดโปรเจกต์
- **อย่าให้มัน "ทำให้ครบ" ในคำสั่งเดียว** — ยิ่งขอบเขตกว้าง ยิ่งมีโอกาสที่มันจะ
  ตัดสินใจแทนคุณในจุดที่คุณควรตัดสินใจเอง
- **หลังจบทุกเฟส ให้ `git diff --stat` ดูเองด้วยตา** ว่าไฟล์ที่ถูกแตะตรงกับที่คาด
