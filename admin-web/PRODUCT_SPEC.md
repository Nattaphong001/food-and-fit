## 1. ภาพรวม (Overview)

**Food & Fit Admin Web** คือเว็บแอปสำหรับผู้ดูแลระบบ (แอดมิน) ของแอปพลิเคชัน
"Food & Fit" — แอปออกกำลังกาย + โภชนาการสำหรับสมาชิกทั่วไป (มือถือ)

โปรเจกต์นี้ถูกสร้างแยกต่างหากจากแอปมือถือที่ใช้งานอยู่แล้ว โดยมีเป้าหมายเดียว:
**ย้ายฟังก์ชันจัดการข้อมูลระบบ (ที่เดิมฝังอยู่ในแอปมือถือ) มาไว้บนหน้าจอกว้าง
(เว็บ, desktop browser)** เพื่อให้แอดมินทำงานจัดการข้อมูลจำนวนมาก
(ท่าฝึก, อาหาร, แผนออกกำลังกาย, สมาชิก) ได้สะดวกกว่าบนมือถือ

**ไม่ใช่** การสร้างฟีเจอร์ใหม่ที่ผู้ใช้ทั่วไปไม่เคยมี — ทุกฟีเจอร์ในเว็บนี้คือ
"เวอร์ชันเว็บของสิ่งที่มีอยู่แล้ว" บวกกับมาตรฐาน UI/ข้อมูลที่รัดกุมขึ้น

### 1.1 ปัญหาที่แก้ (Problem Statement)

- เดิมแอดมินต้องจัดการข้อมูลระบบ (ท่าฝึก/อาหาร/แผน ฯลฯ) ผ่านหน้าจอมือถือที่ไม่เหมาะกับ
  งานกรอกข้อมูล/ตารางจำนวนมาก
- ไม่มีภาพรวมเชิงสถิติ (dashboard/รายงาน) ของระบบทั้งหมดในที่เดียว
- ข้อมูลอ้างอิง (เช่นหน่วยอาหาร, คำอธิบายหมวดคาร์ดิโอ) ไม่ตรงกับพจนานุกรมข้อมูล
  (Data Dictionary) ที่ใช้ในเอกสารวิทยานิพนธ์ ต้องมีช่องทางตรวจสอบ/แก้ให้ตรงกัน

### 1.2 กลุ่มผู้ใช้เป้าหมาย (Target Users)

**แอดมินระบบ** (ตาราง `system_data`) — ใช้งานผ่านเบราว์เซอร์บนคอมพิวเตอร์ ไม่ใช่มือถือ
รองรับ **multi-admin** แล้ว (หลายบัญชีพร้อมกัน, ไม่มี role ย่อย/สิทธิ์ต่างระดับ —
ทุกบัญชีที่ active มีสิทธิ์เท่ากันหมด) ดู [§5.10](#510-จัดการผู้ดูแลระบบ-multi-admin)

## 2. ขอบเขตระบบ (Scope)

โปรเจกต์นี้เป็นส่วนหนึ่งของงานวิทยานิพนธ์ ขอบเขต (บทที่ 1) **ปิดแล้ว** — ฟีเจอร์ใหม่
นอกเหนือจากที่ระบุด้านล่างต้องถามก่อนเสมอ ห้ามเพิ่มเอง (ดู [§7 ข้อจำกัด](#7-ข้อจำกัดและสิ่งที่ตัดสินใจไม่ทำ))

### อยู่ในขอบเขต
- CRUD ข้อมูลอ้างอิงระบบ: กลุ่มกล้ามเนื้อ, ท่าฝึกเวท, การเชื่อมโยงท่าฝึก↔กล้ามเนื้อ,
  หมวดหมู่คาร์ดิโอ, กิจกรรมคาร์ดิโอ, แผนออกกำลังกายมาตรฐาน, หมวดหมู่โภชนาการ,
  ฐานข้อมูลโภชนาการ
- ดูรายชื่อ/รายละเอียดสมาชิก (อ่านอย่างเดียว)
- Dashboard ภาพรวมระบบ + หน้ารายงานเชิงลึก (กราฟ, ช่วงเวลา, export PDF)
- ระบบ login/logout เฉพาะบัญชีแอดมิน
- จัดการบัญชีผู้ดูแลระบบ (multi-admin): เพิ่มบัญชี, ปิดใช้งานบัญชี (soft-delete
  ตาม D-2) — ห้ามลบจริง, ห้ามปิดบัญชีตัวเอง, ห้ามปิดจนไม่เหลือบัญชี active เลย

### นอกขอบเขต (ตัดสินใจแล้วว่าไม่ทำ — ดู §7)
- Import ข้อมูลอาหารแบบ CSV
- สถานะเผยแพร่/ฉบับร่างของแผนฝึก + นับจำนวนผู้ใช้ต่อแผน
- ทำสำเนาแผนฝึก (duplicate plan)
- Undo หลังลบ (delete-toast undo)
- แก้ไข/ลบ/รีเซ็ตรหัสผ่านสมาชิกจากหน้ารายชื่อสมาชิก (by design: read-only)

## 3. สถาปัตยกรรมระบบ (System Architecture)

ระบบทั้งหมดแบ่งเป็น **3 โปรเจกต์แยก directory กัน** ห้ามข้ามไปแก้ของอีกฝั่งโดยไม่ได้รับอนุญาต:

| ส่วน | Path | เทคโนโลยี | วิธีรัน | Port |
|---|---|---|---|---|
| API กลาง | `C:\xampp\htdocs\food_and_fit_api` | Go + MySQL | `go run main.go` | 8081 |
| แอปมือถือ (สมาชิก) | `C:\myFutter68\myapp` | Flutter (mobile) | `flutter run` | - |
| **Admin Web (โปรเจกต์นี้)** | `C:\myFutter68\myapp_admin` | Flutter Web | `flutter run -d chrome --web-port=8090` | 8090 |

```
┌─────────────────────┐        ┌──────────────────────┐
│  Admin Web (Flutter) │──HTTP─▶│   Go REST API (8081)  │──▶ MySQL (food_and_fit_db)
│  localhost:8090      │  JWT   │  ALLOWED_ORIGINS=8090 │
└─────────────────────┘        └──────────────────────┘
                                         ▲
                                         │ HTTP (endpoint เดิม, ห้ามแก้ signature)
                                ┌────────┴─────────┐
                                │  แอปมือถือ (สมาชิก) │
                                └───────────────────┘
```

**กติกาสำคัญ:**
- Admin web และแอปมือถือ **ใช้ API ตัวเดียวกัน (backend เดียว)** แต่แยก endpoint
  ที่ใช้กันชัดเจน — ของใหม่ที่แอดมินต้องการ ให้เพิ่ม endpoint ใหม่ (มักขึ้นต้น `/admin/...`)
  ไม่แก้ endpoint เดิมที่แอปมือถือพึ่งพาอยู่
- Admin web ห้าม copy ไฟล์จากแอปมือถือแบบแก้ไฟล์ต้นทาง — ต้อง copy โค้ดมาไว้ใน
  `myapp_admin` เท่านั้น (เช่น `admin_auth_service.dart` เขียนใหม่แยกจาก
  `myapp/lib/services/auth_service.dart` เพราะของเดิมผูกกับฟีเจอร์ที่แอดมินไม่ใช้)
- CORS: `ALLOWED_ORIGINS` ใน `food_and_fit_api\.env` ต้องตรงกับ port ที่ admin web รัน (8090)

### 3.1 Tech Stack (Admin Web)

- **Framework:** Flutter (Web target)
- **State management:** GetX (`get`, `get_storage` สำหรับ local/session storage)
- **HTTP client:** `ApiClient` wrapper กลาง (`lib/services/api_client.dart`)
- **Charts:** `fl_chart`
- **PDF export:** `printing`/`pdf` (สร้างรายงาน PDF จากหน้า "รายงานระบบ")
- **Auth token:** JWT เก็บใน `GetStorage` (`auth_token`, `user_data`)
- **Remembered credentials:** เก็บผ่าน `flutter_secure_storage` (เข้ารหัส แยกจาก
  token ที่เก็บใน `GetStorage` ธรรมดา เพราะรหัสผ่านดิบไวต่อความปลอดภัยกว่า)
- **Base URL:** `--dart-define=API_BASE_URL=...` (default `http://localhost:8081`)

## 5. รายละเอียดฟีเจอร์ (Feature Specification)

### 5.1 การเข้าสู่ระบบ (Authentication)

| หัวข้อ | รายละเอียด |
|---|---|
| หน้าจอ | `login_view.dart` — ฟอร์ม email/password |
| Endpoint | `POST /api/login` (endpoint เดียวกับที่แอปมือถือใช้ — เช็ค `member_profile` ก่อน ไม่เจอค่อยเช็ค `system_data`) |
| Role guard | ถ้า response `role != 'admin'` → **ไม่เก็บ token เลย** แจ้ง "บัญชีนี้ไม่ใช่บัญชีแอดมิน" |
| Session persist | Token เก็บใน `GetStorage`, refresh หน้าเว็บแล้วไม่หลุด login — validate token ค้างกับ `GET /admin/analytics/overview` ทุกครั้งที่เปิดแอป |
| กรณี server ต่อไม่ได้ตอน validate | ปล่อยให้ยัง login ค้างไว้ก่อน (เหมือนพฤติกรรมฝั่งมือถือ) ไม่บังคับ logout |
| Logout | `POST /api/admin/logout` (revoke token) + เคลียร์ local storage เสมอแม้ network error |
| Remembered credentials | มี service แยก (`remembered_credentials_service.dart`) จำอีเมล/รหัสผ่านที่เคย login สำเร็จ (จำกัดเฉพาะเครื่อง ผ่าน local storage) |

### 5.2 ภาพรวมระบบ (Dashboard)

**หลักการออกแบบ:** "สแกน 5 วินาทีแล้วรู้ว่าระบบปกติหรือไม่" — ไม่ใช่หน้าเจาะข้อมูล
จึงไม่มีตัวกรองช่วงเวลา คงที่ 30 วันล่าสุดจากฝั่ง backend

**เนื้อหา:**
- Stat cards: จำนวนผู้ใช้งานทั้งหมด (+ % เปลี่ยนแปลง), สมาชิกใหม่, สมาชิก active,
  อัตรายืนยันตัวตน (verified rate)
- กราฟ timeline สมาชิกใหม่รายวัน
- Pie chart การกระจายเป้าหมายสมาชิก (ลดน้ำหนัก / เพิ่มกล้ามเนื้อ / รักษาน้ำหนัก)
- ตารางสมาชิกล่าสุด (พร้อมลิงก์ "ดูทั้งหมด" → ไปหน้ารายชื่อสมาชิก)

### 5.3 รายงานระบบ (Reports)

หน้าเจาะลึกกว่า dashboard — มีตัวกรองช่วงเวลา 3 แบบ: **สัปดาห์ / เดือน / กำหนดเอง**
(custom date range พร้อม calendar picker)

**เนื้อหา:**
- Stat cards: ผู้ใช้งาน, ครั้งที่ออกกำลังกาย, แคลอรีรับรวมทั้งระบบ,
  แคลอรีเผาผลาญรวมทั้งระบบ (ทุกกิจกรรม — คำนวณจาก BMR baseline×1.2×วัน active
  + คาร์ดิโอ + เวทเทรนนิ่ง)
- กราฟรายสัปดาห์: แคลอรีรับ vs แคลอรีเผาผลาญ **เฉพาะคาร์ดิโอ** (คนละสูตรกับ stat
  card ด้านบนโดยตั้งใจ — ป้ายกำกับแยกชัดเจนเพื่อไม่ให้สับสน)
- Pie chart สัดส่วนกิจกรรมเวท/คาร์ดิโอ
- **Export PDF** (`รายงานภาพรวม Food & Fit`) — สรุปทุกกราฟ/stat ข้างต้นเป็นไฟล์ PDF ดาวน์โหลดได้

### 5.4 จัดการเวทเทรนนิ่ง

| หน้า | หน้าที่ |
|---|---|
| กลุ่มกล้ามเนื้อ (`manage_muscle_group_view.dart`) | CRUD กลุ่มกล้ามเนื้อ ใช้จัดหมวดท่าฝึก |
| ท่าฝึกเวท (`manage_weight_exercises_view.dart`) | CRUD ท่าฝึกเวทเทรนนิ่ง — รูปภาพ, วิดีโอสอนเต็ม (YouTube URL, ต้องขึ้นต้น `https://` + โดเมน youtube), วิดีโอลูปสั้น (ไฟล์ MP4 อัปโหลด, เล่นระหว่างฝึกจริงในแอปมือถือ), รายละเอียดวิธีฝึก/เทคนิค (multiline textarea) |
| เชื่อมโยงท่าฝึกกับกล้ามเนื้อ (`manage_exercise_muscles_view.dart`) | จับคู่ท่าฝึก ↔ กล้ามเนื้อหลัก/รอง — ตารางอ่านอย่างเดียว + side panel แก้ไขรายท่า, bulk เพิ่มกล้ามเนื้อรองให้หลายท่าพร้อมกัน, filter ตามสถานะเชื่อมโยง (ครบ/ยังไม่ระบุ) |

**กติกาข้อมูล:** ท่าฝึกที่ยังไม่มีการเชื่อมโยงกล้ามเนื้อเลยจะไม่หายไปจากตาราง — แสดงเป็น
แถวพร้อมป้าย "ยังไม่ระบุ" (ให้แอดมินไล่เช็คได้ครบ)

### 5.5 จัดการคาร์ดิโอ

| หน้า | หน้าที่ |
|---|---|
| หมวดหมู่คาร์ดิโอ (`manage_cardio_types_view.dart`) | CRUD หมวดหมู่ ใช้จัดกลุ่มกิจกรรมคาร์ดิโอ |
| กิจกรรมคาร์ดิโอ & METs (`manage_cardio_activities_view.dart`) | CRUD กิจกรรมคาร์ดิโอ พร้อมค่า METs (ใช้คำนวณแคลอรีเผาผลาญ), รูปภาพ, วิดีโอสอน + วิดีโอลูป (เหมือนท่าเวท), คำอธิบาย/เทคนิค (multiline) |

### 5.6 จัดการแผนการฝึก (Workout Plans)

| หน้า | หน้าที่ |
|---|---|
| รายการแผน (`manage_system_workout_plans_view.dart`) | CRUD แผนออกกำลังกายมาตรฐานที่สมาชิกเลือกใช้เป็นแผนเริ่มต้นได้ (ชื่อ, จำนวนวัน/สัปดาห์ 1-7, คำอธิบาย) |
| รายละเอียดแผน (`manage_system_plan_details_view.dart`) | คลิกเข้าไปในแต่ละแผน → กำหนดว่าวันไหนฝึกท่าอะไรบ้าง, จัดลำดับท่าฝึกในแต่ละวัน (ปุ่มเลื่อนขึ้น/ลง), แสดงผลแบบ 2-คอลัมน์บนจอกว้าง |

### 5.7 จัดการโภชนาการ

| หน้า | หน้าที่ |
|---|---|
| หมวดหมู่โภชนาการ (`manage_nutrition_categories_view.dart`) | CRUD หมวดหมู่อาหาร |
| ฐานข้อมูลโภชนาการ (`manage_food_items_view.dart`) | CRUD รายการอาหาร — ชื่อ, แคลอรี, สารอาหาร (โปรตีน/คาร์บ/ไขมัน), รูปภาพ, **หน่วยนับ** (dropdown จำกัดเฉพาะ "กรัม"/"ออนซ์" ตามข้อมูลจริงในฐานข้อมูล — ออนซ์ใช้กับเครื่องดื่มเท่านั้น) |

### 5.8 จัดการสมาชิก (อ่านอย่างเดียว)

| หน้า | หน้าที่ |
|---|---|
| รายชื่อสมาชิก (`manage_members_view.dart`) | ค้นหา/กรองสมาชิก — **read-only ตามสเปก** ไม่มีแก้ไข/ลบ/รีเซ็ตรหัสผ่านจากหน้านี้ |
| รายละเอียดสมาชิก (`member_detail_view.dart`) | โปรไฟล์ + ข้อมูลร่างกายล่าสุด + กราฟย้อนหลัง BMI/BMR/TDEE ของสมาชิกคนเดียว |

### 5.9 ข้อมูลระบบ / โปรไฟล์แอดมิน

`admin_profile_view.dart` — เข้าถึงผ่านคลิก avatar ที่ topbar เท่านั้น (ไม่อยู่ใน sidebar)
อิงตาราง `system_data` แถวเดียว (ไม่มี multi-admin) แบ่ง 3 การ์ด:
1. **บัญชีของฉัน** — อีเมล (read-only), ชื่อ-สกุล
2. **ข้อมูลหน่วยงาน** — ชื่อหน่วยงาน, วันที่เริ่มงาน (ปุ่มบันทึกร่วมกับการ์ดที่ 1 — บันทึกผ่าน `PUT /admin/profile` เดียวกัน)
3. **ความปลอดภัย** — เปลี่ยนรหัสผ่าน (มีแถบวัดความหนักแน่นรหัสผ่าน, ยืนยันด้วย confirm dialog ก่อนบันทึกจริง)

### 5.10 จัดการผู้ดูแลระบบ (Multi-admin)

`manage_admins_view.dart` — เมนูแยกจาก "ข้อมูลระบบ/โปรไฟล์แอดมิน" (§5.9)
โปรไฟล์ = ข้อมูลของบัญชีตัวเอง, หน้านี้ = จัดการ**บัญชีอื่น**ทั้งหมดในระบบ

| หัวข้อ | รายละเอียด |
|---|---|
| รายการ | ตาราง: อีเมล, ชื่อ-นามสกุล, หน่วยงาน, วันที่เริ่มใช้งาน, สถานะ (ใช้งานอยู่/ปิดใช้งาน) + ค้นหาชื่อ/อีเมล |
| เพิ่มบัญชี | ฟอร์ม: อีเมล, ชื่อ-นามสกุล, หน่วยงาน (ไม่บังคับ), วันที่เริ่มใช้งาน (ไม่บังคับ), รหัสผ่าน (ตั้งเองโดยแอดมินที่เพิ่ม ≥ 8 ตัวอักษร) — ระบบไม่ส่งอีเมล/OTP ยืนยัน ต้องแจ้งรหัสผ่านให้เจ้าของบัญชีเองนอกระบบ |
| ปิดใช้งานบัญชี (soft delete, D-2) | ปุ่ม "ปิดใช้งาน" ต่อแถว พร้อม confirm dialog — **ไม่มีลบจริง** |
| กันตัวเอง | ปิดใช้งานบัญชีของตัวเองไม่ได้ (ปุ่ม disabled) |
| กันเหลือ 0 แอดมิน | ฝั่ง server บังคับด้วย transaction + `FOR UPDATE` ห้ามปิดจนไม่เหลือบัญชี active เลย — หน้านี้กันซ้ำ/แจ้งเหตุผลเบื้องต้นเท่านั้น |
| Role | ไม่มี role ย่อย — ทุกบัญชี active มีสิทธิ์เท่ากันหมด (ไม่ใช่ super-admin vs admin) |

## 6. มาตรฐาน UI/UX (Design System)

- **Responsive breakpoints** กำหนดกลางที่ `core/constants/layout_breakpoints.dart`
  ปรับ layout ตามความกว้างจอ (เช่น sidebar ยุบเป็นเมนู hamburger, การ์ดสลับจาก 3
  คอลัมน์เหลือ 1 คอลัมน์บนจอแคบ)
- **Theme กลาง** ที่ `core/theme/theme.dart` (สี, ตัวอักษร, spacing รวมศูนย์ — ทุกหน้า
  ต้อง reuse ไม่ประกาศสีซ้ำเอง)
- **Widget กลางที่ใช้ร่วมกันทุกหน้าตาราง/ฟอร์ม:**
  `AdminDataTable`, `AdminFilterBar`, `AdminPageHeader`, `AdminPaginationBar`,
  `AdminIconCard`, `AdminIconListTile` (การ์ดแนวนอนกะทัดรัด — ใช้แทน `AdminIconCard`
  เมื่อรายการน้อย/ไม่ต้องการพื้นที่ไอคอนใหญ่), `AdminListState` (สถานะ
  loading/empty/error ที่ใช้ร่วมกันทุกหน้า), `AppConfirmDialog`, `TopFlash`
  (toast แจ้งเตือน, ตั้งใจไม่มีปุ่ม undo)
- ตารางทุกหน้ามี hover highlight ทั้งแถว + cursor pointer, header ไม่ล้น 2 บรรทัด
- ฟอร์มมี client-side validation ก่อนส่ง (เช่น จำนวนวัน/สัปดาห์เป็น stepper 1-7,
  ความยาวชื่อ/คำอธิบายขั้นต่ำ)
- การลบทุกจุดต้องผ่าน confirm dialog ก่อนเสมอ ไม่มี undo หลังลบ (เป็นการตัดสินใจ
  ออกแบบ ไม่ใช่ของที่ยังไม่ได้ทำ)

### 6.1 รูปแบบ Navigation หมวดหมู่ → รายการย่อย (Drill-down)

หน้าหมวดหมู่ (category list) ทุกคู่ในระบบใช้กลไก **เดียวกัน** ในการเจาะลึกไปหน้ารายการย่อย:
เก็บ id/ข้อมูลที่คลิกไว้เป็น local state (`setState`) แล้วให้ `build()` คืน widget
ปลายทางแทนที่เนื้อหาเดิม **ในสล็อตเดิมของ `IndexedStack`** ที่ sidebar shell ดูแลอยู่ —
**ไม่ใช้ `Get.to()` push route ใหม่** (เคยใช้มาก่อน 2026-08-29 แต่ทำให้ sidebar หายไปทั้งจอ
ตอน drill-down จึงเปลี่ยน) sidebar จึงเห็นตลอดเวลา ปุ่ม `AppBackButton` ของหน้าเป้าหมาย
เรียก callback `onBack` ที่หน้าต้นทางส่งมา (แทน `Navigator.pop`) เพื่อ `setState` เคลียร์ตัวกรอง
กลับไปแสดงลิสต์หมวดหมู่เดิม

คู่ที่ใช้แพทเทิร์นนี้ (ยืนยันแล้วในโค้ด ณ 2026-08-29):

| หมวดหมู่ (ต้นทาง) | รายการย่อย (ปลายทาง) | วิธีส่งค่ากรอง |
|---|---|---|
| กลุ่มกล้ามเนื้อ | ท่าฝึกเวท | `ManageWeightExercisesView(initialMugId:, onBack:)` |
| หมวดหมู่คาร์ดิโอ | กิจกรรมคาร์ดิโอ | `ManageCardioActivitiesView(initialCatId:, onBack:)` |
| หมวดหมู่โภชนาการ | ฐานข้อมูลโภชนาการ | `ManageFoodItemsView(initialCategoryId:, onBack:)` |
| รายการแผน (แผนระบบ) | รายละเอียดแผนระบบ | `ManageSystemPlanDetailsView(planId:..., onBack:)` (ค่าที่จำเป็นครบ ไม่มีโหมด standalone) |
| รายชื่อสมาชิก | รายละเอียดสมาชิก | `MemberDetailView(memberId:..., onBack:)` (ค่าที่จำเป็นครบ ไม่มีโหมด standalone) |

**หมายเหตุ:** 3 คู่แรก (กล้ามเนื้อ/คาร์ดิโอ/โภชนาการ) ปลายทางมีโหมด "standalone" ด้วย
(เข้าถึงตรงจาก sidebar แบบไม่กรอง, `onBack == null`) มี flag `isDrillDown` ภายในคุมแค่
การแสดงปุ่ม back — ไม่มี `Scaffold` ของตัวเองเลย (ใช้ของ shell) ส่วน "รายละเอียดแผนระบบ"
มี `Scaffold` ของตัวเอง (ให้ `AppFab` วางตำแหน่งได้) แต่เป็น Scaffold ที่ฝังอยู่ในสล็อตของ
shell ไม่ใช่ Scaffold ระดับ route — ไม่ได้ทำให้ sidebar หาย เพราะขนาดถูกจำกัดด้วย
constraints จาก parent เสมอ

## 7. ข้อจำกัดและสิ่งที่ตัดสินใจไม่ทำ

รายการนี้ผ่านการพิจารณาโดยทีมแล้วว่า **อยู่นอกขอบเขตวิทยานิพนธ์ (บทที่ 1)** —
ถ้ามีคนเสนอฟีเจอร์เหล่านี้อีกในอนาคต ให้ตอบกลับด้วยเหตุผลนี้แทนการทำเลย:

| ฟีเจอร์ที่ไม่ทำ | เหตุผล |
|---|---|
| Import อาหารแบบ CSV | ไม่อยู่ในขอบเขตที่ประกาศไว้ ความเสี่ยงสูง (ต้องเขียน parser/validation ใหม่) เทียบกับคะแนนที่ได้ต่ำ |
| Persisted icon picker (คาร์ดิโอ/โภชนาการ) | Cosmetic เท่านั้น ไม่คุ้มกับต้องแก้ schema + ER Diagram + บทที่ 4 |
| สถานะ publish/draft ของแผน + นับผู้ใช้ต่อแผน | ไม่ใช่ส่วนหนึ่งของฟังก์ชัน "จัดการตารางการออกกำลังกาย" ที่ประกาศไว้ ต้องเพิ่มคอลัมน์ + endpoint ใหม่ |
| Undo หลังลบ (5 วินาที) | ตั้งใจออกแบบให้การลบเป็นการกระทำสุดท้าย (final) ไม่ใช่ของที่ยังทำไม่เสร็จ |
| ทำสำเนาแผน (duplicate plan) | ความซับซ้อนไม่คุ้มประโยชน์ (ต้อง copy ท่าฝึก/วันฝึกลูกทั้งหมดด้วย) |
| แก้ไข/ลบ/รีเซ็ตรหัสผ่าน จากหน้ารายชื่อสมาชิก | ออกแบบให้อ่านอย่างเดียวตั้งแต่ต้น ต้องมี backend endpoint ใหม่ที่ยังไม่มี |

### กฎเหล็กของโปรเจกต์ (ไม่ขึ้นกับฟีเจอร์ ใช้ตลอดทั้งงาน)

1. ห้ามแก้ไฟล์ในแอปมือถือ (`myapp`) — ต้อง copy โค้ดมาแก้ที่ `myapp_admin` เท่านั้น
2. ห้ามแก้ signature/response ของ endpoint เดิมที่แอปมือถือใช้ — ต้องการอะไรเพิ่มให้เพิ่ม endpoint ใหม่
3. ห้ามเขียนสูตรคำนวณ (BMR/TDEE/Target/METs/1RM/Macronutrients) ซ้ำที่อื่น — ต้องเรียก `CalculateGoals` ใน `services/calculator.go` เสมอ
4. ตารางแม่ (`nutrition`, `cardio`, `nutrition_category`, `cardio_category`) ไม่มี `created_at`/`updated_at` — เรียง "ล่าสุด" ด้วย `PK DESC` เท่านั้น
5. ลบข้อมูลที่มี FK ผูกอยู่ (เช่นอาหารที่มีคนกินไปแล้ว) → **soft delete** (คอลัมน์ status/hidden) ไม่ใช่ลบจริง
6. Refactor/ย้ายโค้ดชุดใหญ่ → ทำทีละไฟล์/ทีละ endpoint เสมอ
7. เจอโค้ดจริงไม่ตรงกับ Data Dictionary (บทที่ 4) → หยุดแล้วรายงาน ห้ามเดาแก้เอง

## 8. ความเสี่ยง/ประเด็นที่ยังไม่ปิด ณ วันที่จัดทำเอกสาร

- **Custom Reports QA**: bug เดียวที่พบจากภาพหน้าจอ (calendar view overflow) แก้แล้ว
  แต่ยังไม่มีการทดสอบ regression ครบทุกเคสของหน้ารายงาน
- **บทที่ 4 (Data Dictionary)**: มีการเปลี่ยน schema เล็กน้อยระหว่างทาง (soft-delete
  column, + ตาราง/คอลัมน์รองรับ multi-admin ใน `system_data`) ที่ต้องอัปเดตเอกสาร
  วิทยานิพนธ์ตามหลัง — เอกสาร Word/PDF อยู่นอก repo ทั้งสอง (`myapp_admin`,
  `food_and_fit_api`) ต้องแก้ด้วยมือแยกต่างหาก
- **`lib/core/utils/csv_download_web.dart`**: มีฟังก์ชัน `downloadCsv()` พร้อมใช้
  (เขียนไว้แล้ว, BOM UTF-8 รองรับภาษาไทยใน Excel) แต่ **ยังไม่มีหน้าไหนเรียกใช้จริง**
  — โค้ด dead ค้างอยู่ ยังไม่ชัดว่าจะเป็น export หน้าไหน ต้องถามก่อนต่อยอด/ลบ
- **เครื่องมือทดสอบ (ไม่ใช่ส่วนของแอป)**: `testsprite_tests/` (test suite อัตโนมัติ
  จาก TestSprite MCP) และ `tool/serve_web.py` (serve `build/web` แบบ multi-thread
  สำหรับรัน TestSprite ขนาน) — เป็นเครื่องมือ dev/QA ไม่ใช่ฟีเจอร์ของระบบ

## 9. สรุป Endpoint หลักที่ Admin Web เรียกใช้

| Endpoint | ใช้ที่ |
|---|---|
| `POST /api/login` | Login (ใช้ร่วมกับแอปมือถือ) |
| `POST /api/admin/logout` | Logout |
| `GET /api/admin/analytics/overview` | Validate session ค้าง (ไม่มี query param) + หน้ารายงาน (`?start=&end=`) |
| `GET /api/admin/dashboard/summary` | หน้าภาพรวมระบบ (§5.2) — คนละ endpoint กับหน้ารายงาน |
| `PUT /api/admin/profile` | บันทึกข้อมูลระบบ/โปรไฟล์แอดมิน (ของบัญชีตัวเอง) |
| `GET /api/admin/admins` | รายการบัญชีแอดมินทั้งหมด (§5.10) |
| `POST /api/admin/admins` | เพิ่มบัญชีแอดมินใหม่ |
| `PUT /api/admin/admins/:id/deactivate` | ปิดใช้งานบัญชีแอดมิน (soft delete) |
| CRUD ต่างๆ ใต้ `/api/admin/...` | กลุ่มกล้ามเนื้อ, ท่าฝึก, การเชื่อมโยง, คาร์ดิโอ, แผนฝึก, โภชนาการ, สมาชิก (ตามรายชื่อในหมวด 5) |

> รายชื่อ endpoint แบบเต็มดูได้จาก `routes/api.go` ฝั่ง `food_and_fit_api` — ไม่ได้
> คัดลอกทั้งหมดมาในเอกสารนี้เพราะเปลี่ยนบ่อยกว่าฟีเจอร์ ให้ใช้โค้ดจริงเป็น source of truth
